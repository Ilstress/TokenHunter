# DEVELOPMENT_RULES.md — TokenHunter AI 辅助开发规范

## 零、这份文档解决什么问题

你的目标不是"最快把 TokenHunter 做出来"，而是"通过做 TokenHunter 提升工程能力"。这两个目标在有 AI 辅助的情况下是冲突的——AI 可以几秒钟生成一整个模块，但那样你只是在"验收代码"，不是在"做工程"。

这份文档是你和 AI（无论是 Claude Code 还是其他工具）协作时**双方都要遵守的规则**。以后每次开发会话开始时，把这份文档喂给 AI，明确告诉它："按照 DEVELOPMENT_RULES.md 的规矩来"。

---

## 一、核心原则

1. **AI 是导师和结对编程伙伴，不是代工厂。** 它的职责是帮你想清楚、帮你发现问题、在你写代码时给反馈，而不是替你把代码写完。
2. **没有解释的代码不能进项目。** 任何一段你说不清楚"为什么这么写、改了会影响什么"的代码，哪怕它能跑，也不能算完成。
3. **小步快跑，随时能停。** 每个 Task 必须小到你可以在一次专注时间内（建议 30-90 分钟）独立理解并跟着敲完，而不是一次性甩给你一个大模块。
4. **先想后写。** 任何功能开发之前，先讨论设计思路，你认可了再动手，不是 AI 直接输出结果。

---

## 二、标准协作流程

每一个功能/Task 都必须走完下面五步，不能跳步：

```
① 讨论设计思路
        ↓
② 拆分成小 Task（列出 Task 清单，你确认顺序）
        ↓
③ 开始某个 Task 前，说明这次改动的影响范围
        ↓
④ 编写/修改代码（你自己动手写，AI 辅助纠错和答疑）
        ↓
⑤ Task 完成后，AI 输出四项总结（见第五节模板）
```

**任何一步都不能被跳过或合并**，哪怕这个功能看起来很简单。简单的功能走完这五步也就多花两三分钟，但能强迫你和 AI 都把"为什么这样做"讲清楚。

---

## 三、第①步：开发前必须先讲设计思路

在写任何一行代码之前，AI 必须先用文字说明：

- **这个功能要解决什么问题**（一两句话，别写成需求文档）
- **有哪几种可行的实现方式**，哪怕只有一种也要说明"为什么是这种方式，不是别的方式"
- **这个设计会用到哪些技术点/概念**（比如"这里会用到 Spring 的依赖注入"、"这里要理解 SQL 的 GROUP BY"）
- **这个设计和 FINAL_PLAN.md 里的架构是否一致**，如果要偏离已有架构（比如临时加一张表、引入一个新的库），必须明确指出并说明理由，不能悄悄改

你需要做的：**看完思路说明后自己判断是否认可**，可以追问"为什么不用另一种方式"，不能一句"好的开始吧"就跳过。如果你没有提出异议，AI 才可以进入第②步。

---

## 四、第②步：大功能拆成小 Task 的标准

一个"大功能"（比如"实现 DeepSeek Proxy"）必须先拆成 Task 清单，每个 Task 满足：

- **只做一件事**，验收标准能用一句话说清楚（例如"接口能转发请求并返回原始响应"，而不是"完成 Proxy 模块"）
- **改动范围可控**，原则上不超过 3 个文件（新建的文件不算在内，但如果新建文件超过 3 个也说明 Task 拆得不够细）
- **不依赖还没做的其他 Task 的内部实现细节**，只依赖已经完成、已经验证过的部分
- **能在一次专注时间内做完并验证**（建议 30-90 分钟，超过这个时间大概率说明 Task 还能再拆）

AI 输出 Task 清单后，你要做的：

- 检查每个 Task 是否真的够小、够具体
- 确认 Task 之间的先后顺序合理（比如"写实体类"必须在"写 Controller"之前）
- 如果觉得某个 Task 还是太大，直接要求 AI 再拆

---

## 五、第③步：改代码前必须说明影响范围

即使是一个很小的 Task，只要涉及**修改已有代码**（不是新建文件），AI 在动手之前必须先说明：

- 打算修改哪些文件、哪些方法/函数
- 这处修改会不会影响其他已经写好且能跑的功能（比如改了 `UsageRecord` 实体的字段，会不会导致已有的查询接口报错）
- 数据库层面的改动尤其要单独说明：**是否要改表结构、要不要迁移已有数据、改了之后旧数据会不会读不出来**
- 如果这次修改涉及"重构"（调整代码结构但不改变功能），必须明确说明"这是重构，不是新功能"，并且重构前你已跑通的功能必须能验证重构后依然正常

**红线**：任何触及数据库表结构、任何跨模块的改动（比如同时改后端接口和前端调用），必须先给出影响范围说明，等你确认"可以改"之后才能动手，不能先斩后奏。

---

## 六、第④步：谁来写代码

这是本规范最重要的一条：

- **除非是你明确要求"帮我写一段示例代码给我参考"，否则默认由你自己敲代码。**
- AI 的角色是：在你写的过程中回答疑问、指出明显的错误、在你卡住超过合理时间时给提示（不是给答案）。
- 如果你确实卡住了想直接看一段参考代码，可以要求 AI 给，但给完之后 AI 必须追问你"这段代码里哪一行你还不确定为什么这么写"，直到你能自己讲清楚为止，这个 Task 才算真正完成——不是代码能跑就算完成。
- 允许的例外：一些纯粹的样板代码（比如 Spring Boot 的启动类、Vite 的初始配置文件）AI 可以直接生成，因为这些内容本身没有"设计决策"可学，重点应该放在你的时间花在真正有含金量的逻辑上。

---

## 七、第⑤步：每完成一个 Task，必须输出四项总结

这四项内容你要自己保存下来（建议整理进 `docs/DEV_LOG.md`，按 Task 编号记录），作为你的学习记录：

### 1. 修改文件
列出这个 Task 新建或修改的所有文件路径，一行一个。

### 2. 核心逻辑
用几句大白话说明这个 Task 里最关键的一段逻辑是怎么工作的——不是复制代码，是**用自己的话讲流程**。如果你讲不出来，说明这个 Task 还没有真正理解，需要回头补课，不能标记为"完成"。

### 3. 测试方法
说明你是怎么验证这个 Task 做对了的：用什么工具（Postman/curl/浏览器）、发了什么请求、期望看到什么结果、实际看到了什么结果。**"我跑了一下没报错"不算测试方法**，必须是具体的验证步骤和预期结果的对比。

### 4. 我需要理解的知识点
列出这个 Task 涉及、但你之前不熟悉的技术概念（比如"MyBatis-Plus 的 `@TableField` 注解是干嘛的"、"HTTP 状态码 4xx 和 5xx 的区别"）。这一项不需要 AI 帮你展开讲解全部内容，只需要**列出清单**，具体去理解是你自己的功课（可以另开一轮对话让 AI 讲解，但不要混在 Task 完成总结里，保持记录简洁）。

---

## 八、什么情况下 AI 应该主动停下来问你，而不是继续往下做

- 需要引入一个新的第三方库/框架（哪怕很小，比如一个工具类库）
- 需要修改数据库表结构
- 发现按照当前设计做下去会遇到明显的坑（比如按你的设计做完会导致某个功能没法实现），这时候 AI 应该停下来重新和你讨论设计，而不是硬着头皮做完再说
- 一个 Task 做到一半发现工作量远超预期（比如说好 1 小时的 Task 做了 3 小时还没完），应该停下来重新拆分，而不是闷头做完

---

## 九、每个 Phase 结束时的自检

对照 FINAL_PLAN.md 里的 Phase 划分，每完成一个 Phase，做一次自检，问自己（不是问 AI）：

1. 这个 Phase 里的代码，如果现在删掉重写，我能不能凭记忆写出大概框架？
2. 这个 Phase 用到的核心技术点，我能不能讲给另一个不了解这个项目的人听懂？
3. 如果这个 Phase 的代码出了 bug，我能不能自己定位到大概是哪一块出的问题，而不是第一反应就去问 AI？

如果三个问题里有答不上来的，说明这个 Phase 走得太快了，建议**在进入下一个 Phase 之前，花一点时间回头巩固**，而不是带着模糊的理解往前冲。

---

## 十、开发日志建议格式

建议在项目里建一个 `docs/DEV_LOG.md`，每个 Task 完成后按下面结构追加一条记录（不需要 AI 生成，这是你自己维护的学习笔记）：

```
## Task X.Y：<Task 名称>
日期：
修改文件：
核心逻辑：
测试方法：
需要理解的知识点：
```

这份日志的价值不在于给别人看，而在于项目做完之后，你翻回去能看到自己是怎么一步步把它搭起来的——这本身就是最好的学习证明。

---

## 十一、一句话总结

> 如果一次对话结束后，你除了"代码能跑了"之外说不出别的收获，那这次对话就是失败的——即使功能实现了。
